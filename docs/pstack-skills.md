# How pstack fits alongside Matt Pocock's skills

Reviewed on 2026-10-01. This catalogue covers all 47 skill files in the standalone pstack mirror, 24 workflow skills and 23 principles. I read the checked-out skill files and relevant reference files, and compared them with all 37 skill files in Matt's checkout, including his in-progress skills. The descriptions below report what the files prescribe. The recommendation columns are my assessment for this dotfiles setup.

## The recommended combination

Keep Matt's idea-to-spec-to-tickets-to-implementation flow. Add pstack's focused tools for explaining existing code, recovering design rationale, writing technical documentation, creating reusable app-verification instructions, and checking TypeScript design.

The additions managed through dotfiles are `how`, `why`, `technical-writing`, `create-verification-skill`, `maintain-verification-skill`, `typescript-best-practices`, `principle-type-system-discipline`, and `principle-boundary-discipline`. The last two support the TypeScript skill. The existing `unslop` remains the provider for pstack's writing dependencies. These additions do not activate `poteto-mode` or install all of pstack.

`show-me` is already installed. It draws the smallest useful diagram, code sketch, or focused HTML artifact to explain the current topic. pstack's `show-me-your-work` keeps a TSV decision log, checks that log against the conversation transcript, and asks another model to review it. They have different jobs and different names. Matt's `pr` skill explicitly credits Humanlayer's `show-me` for its visual summary patterns. [Matt's pr skill](https://github.com/mattpocock/skills/blob/d81f3a183412e71a5b1e84ca21bc1a35eea03a60/skills/engineering/pr/SKILL.md), [pstack show-me-your-work](https://github.com/backnotprop/pstack/blob/157aae39a733135e93d8b5b19ff62c6a84b0ad56/skills/show-me-your-work/SKILL.md).

## Dependencies and setup limits

The mirror's README contains a convenient installation table, but it is not a complete dependency graph. The skill bodies contain additional references. Distinguish a skill that explicitly calls another workflow from a principle that points to more reading. [Mirror README](https://github.com/backnotprop/pstack/blob/157aae39a733135e93d8b5b19ff62c6a84b0ad56/README.md).

| Starting skill | Required or explicitly used material | Conditional or supporting material |
|---|---|---|
| `how` | Its bundled explorer and explainer prompts; subagent support or the documented sequential fallback. | Per-role model configuration. No other pstack workflow is required. |
| `why` | Its bundled investigator, synthesis, confidence, and source playbooks; git history and source-control investigation. | Connected MCP evidence sources. Missing categories are coverage gaps to report, not a reason to invent evidence. `how` is the documented companion, not an invocation in `why`'s steps. |
| `technical-writing` | Calls `unslop` for AI-pattern cleanup. | Can work with Matt's PR template or writing-for-agents guidance. |
| `typescript-best-practices` | Explicitly applies `principle-type-system-discipline` first and refers to `principle-boundary-discipline`; bundled `references/patterns.md`. | The type-system principle links to `principle-encode-lessons-in-structure` for schema ownership. That is supporting reading, not mandatory execution of another task. |
| `create-verification-skill` | Bundled feature-map examples and access to a real project that can build and run. Must execute one generated proof. | Points to `maintain-verification-skill` for upkeep. It does not invoke maintenance during generation. |
| `maintain-verification-skill` | An existing project verification skill with a feature map and an app that can be exercised. | Points to generation if no target exists. Does not require generating a new skill during maintenance. |
| `teach` | Calls `how` and `why`, applies `unslop`. | A small question may need only one investigation. Uses diagrams and sometimes image generation. |
| `architect` | Calls `how` and `arena`; bundled runner and rationale references. | Calls `why` when ownership or layering changes; `interrogate` for pressure on a design. References several architecture principles. |

The selected subset resolves its model choices through `~/.agents/pstack-models.md`. Dotfiles sets these four roles to `inherit-parent`:

```text
how explorer: inherit-parent
how explainer: inherit-parent
why investigators: inherit-parent
why synthesizer: inherit-parent
```

This keeps `how` and `why` from trying to spawn the Cursor-specific Grok and Claude defaults. It also means these roles use the current chat's model family. Installing their prompt files does not grant access to another provider. The [setup instructions](https://github.com/backnotprop/pstack/blob/157aae39a733135e93d8b5b19ff62c6a84b0ad56/skills/setup-pstack/SKILL.md) define `inherit-parent` as omitting the subagent model override. The [mode's model-routing instructions](https://github.com/backnotprop/pstack/blob/157aae39a733135e93d8b5b19ff62c6a84b0ad56/skills/poteto-mode/SKILL.md) define the same alias for routed roles.

The standalone `how` and `why` files tell other environments to read the settings and use configured roles, but they do not each repeat the omit-model explanation. Read them together with the settings comment and setup instructions. Their prompt templates still use tool names such as Read, Grep, and Glob; a Codex environment needs to use the equivalent available filesystem tools. `why` also contains a Cursor-specific claim that read-only agent mode removes MCP access. Other environments should preserve available MCP access and the investigators' read-only behavior rather than assume the Cursor tool behavior applies everywhere. [how](https://github.com/backnotprop/pstack/blob/157aae39a733135e93d8b5b19ff62c6a84b0ad56/skills/how/SKILL.md), [why](https://github.com/backnotprop/pstack/blob/157aae39a733135e93d8b5b19ff62c6a84b0ad56/skills/why/SKILL.md).

The TypeScript skill's YAML contains `paths` for `.ts` and `.tsx`, but also `disable-model-invocation: true`. Its description says to apply it when reading or editing TypeScript. Do not infer that installation alone makes every Claude/Codex TS edit load it automatically. Use it explicitly, or connect it to the relevant review instructions if you later want automatic coverage. [TypeScript frontmatter](https://github.com/backnotprop/pstack/blob/157aae39a733135e93d8b5b19ff62c6a84b0ad56/skills/typescript-best-practices/SKILL.md).

One source example needs judgment. The TS pattern file claims that replacing `end` with a plain numeric `durationMs` makes negative time ranges unconstructable. A plain `number` still permits negative values. The example does not prove that invariant; boundary validation or a properly validated representation remains necessary. This is a limitation of the example, not a reason to reject the useful type-design guidance. [Time-range example](https://github.com/backnotprop/pstack/blob/157aae39a733135e93d8b5b19ff62c6a84b0ad56/skills/typescript-best-practices/references/patterns.md).

## What I would consider next

The next additions I would consider are `blast-radius` for risky changes, `recall` for recovering work spread across sessions, and `interrogate` for a deliberate second review of a consequential diff. Add them when one of those needs recurs. `arena` and `show-me-your-work` become worthwhile when comparing independent attempts or auditing a long run is worth the extra model calls and artifacts.

Keep the default implementation route unambiguous. Matt owns `tdd` and `teach`; the existing Cursor-derived copy owns `unslop`; the selected pstack skills add specialized tools. Do not install every principle or enable `poteto-mode` merely to use `how`, `why`, the verification generators, or the TypeScript checklist.
